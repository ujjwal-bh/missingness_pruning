# Source data reconstruction and analysis entry points

This archive preserves source extraction, SQL, mapping and cohort logic. It does not contain credentialed data, database dumps, patient partitions, fitted weights or prediction rows. No password is stored. No fresh PostgreSQL import or raw-data rebuild was executed for this publication package. Reproducing all raw stages requires the documented historical database state; do not run archived generated SQL blindly in an existing database.

## Raw prerequisites
MIMIC-IV version 3.1 (`hosp` and `icu` CSV gzip folders) and eICU-CRD version 2.0 (CSV gzip files), obtained separately under PhysioNet access terms. Historical source folders were MIMIC-IV-DATA and EICU-CRD beneath the research root. PostgreSQL 18 was used locally. Schemas were landmark_mimic48 and eicu_landmark in landmark_research. The patient selection hash seed and eligibility definitions are in 05_harmonize_patient_contribution.sql. The study here uses only 24 hours; the shared source infrastructure also produced 12, 36 and 48 hours.

## Historical order
1. `prepare_landmark_import.py --source SOURCE --output STAGING`: stream the adult MIMIC subset; no DB connection. `import_sql_incremental.py` and `import_landmark_data.ps1` generate/execute resumable import SQL, verify imported tables and remove committed staging CSVs. Review paths and capacity settings first. The latter script deletes successfully imported staging files as originally authorized; it is archived for provenance and is not run by this package.
2. `04_apply_primary_death_chronology_exclusion.sql`: exclude stays with recorded death before admission before patient selection. Base eligibility SQL is generated by prepare_landmark_import.py. Do not interpret chronology flags as absence of ICU admission.
3. `prepare_harmonized_cohorts.py`, then its generated eicu_metadata_stage/import_and_harmonize.sql: import eICU patient/hospital metadata and apply hospital-priority patient contribution rules in both databases. Eligibility is applied before fixed hospitalization hash priority, then earliest eligible ICU within that hospitalization. Use 05_harmonize_patient_contribution.sql as the authoritative selection definition.
4. `build_mimic_candidate_features_sql.py`, then 07_build_mimic_core_candidate_features.sql: build MIMIC core observations/features with item IDs, units, numerical screening, ICU/admission joins and landmark availability. eICU: prepare_eicu_core_measurements.py generates selected staging and build_eicu_candidate_features_sql.py generates eicu_core_stage/import_and_build.sql. Run its generated SQL only after staging is complete.
5. `prepare_eicu_lab_unit_correction.py`, then 08_correct_eicu_lab_unit_aliases.sql: preserve accepted equivalent unit aliases. `prepare_eicu_nursing_temperature.py`, then eicu_temperature_stage/import_and_build_temperature.sql: add explicitly labelled Celsius nursing observations. Final eICU core table is core_features_candidate_v3, MIMIC is core_features_candidate_v1.
6. The historical full CSV exporter joined GCS/support candidate tables even though this pruning study uses none of those fields. To recreate its EXACT bytes, extension source preparation/audits, 13_build_gcs_candidates.sql and 14_build_support_documentation_candidates.sql must also be completed. Their staging depends on prepare_extension_source_audit.py, prepare_gcs_candidate_sql.py and prepare_support_documentation_sql.py. These are provided as upstream dependencies, not new predictors for this article.
7. `prepare_model_feature_audit.py` generates 15_final_feature_audit_and_export.sql, which audits cohorts, assigns patient-stable MIMIC source splits and exports two full candidate CSVs. Review generated paths before execution. The original psql COPY format, row order and complete landmarks/columns determine byte hashes. Matching the 24-hour clinical cells alone does not imply matching full-export bytes.
8. Verify exact input hashes in config/export_verification_confirmed_2026_10_15.json. Hashes and mapping provenance are also in aggregate_results/preparation/source_hashes.json. A legitimately changed export needs a new documented version and audit; never disable checks to force a match.

## Analysis from validated feature exports

Use tools/prepare_workspace.py from the repository root with --research-root and a NEW external --work-dir. This stages the code and validates the two original CSV hashes before copying records. Follow the prepare, train, evaluate and robustness commands in the repository README through tools/run_study.py. requirements.txt records observed versions. The 13 method tests use tools/run_tests.py and synthetic fixtures; no aggregate metric fixture is needed for those tests.

The source validation patients are not used for fresh tuning. Target adaptation outcomes are not parsed for indicator selection. New private runs and all existing research data remain outside the Git checkout. Historical Python syntax trees are preserved after comment cleanup, but code hashes and new run identities differ.

## Verification scope
The package verifier reconstructs numerical summaries from aggregate evidence without any patient data. Synthetic tests check selector and resampling behavior. Historical same-workflow verification already replayed/reconciled the original fitted study and 400 robustness checkpoints. This repository organization runs the aggregate verifier and portable synthetic tests; it does not repeat the many-hour model refits or certify the historical mapping as clinically optimal. Fresh raw timestamp/staleness and independent clinical plausibility audits were not performed for this article.


## Code repository working layout

The files in source_preparation are historical inputs and generators, with hash-bound reference files preserved verbatim. Generated SQL contains historical local paths; review connection, staging and output paths in a private source workspace before execution. Some historical import routines delete verified staging files after a committed import. They are not executed by the repository test or model commands. Do not run source generators inside the Git checkout. prepare_workspace.py stages these files into a separate private directory. The current model stages start from validated feature exports, not a certified one-command rebuild from raw CSVs. No new raw-source rebuild was performed during repository organization.
